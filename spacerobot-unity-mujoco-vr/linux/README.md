# Space service robot in Unity with MuJoCo: Linux

The robot runs on MuJoCo 3.11 inside Unity, through the `org.mujoco` plug-in. The MJCF model is imported as Unity components and `MjScene` calls into the MuJoCo C library directly. Unity's PhysX solver plays no part: the scene has no rigidbodies and no colliders, so every contact force comes from MuJoCo, at the 1 ms physics rate.

The autonomous cap-service mission, written in Python against the same model, has been rewritten in C# and runs in the same process.

## Running

Requirements are Ubuntu 24.04 x86_64, and for the project Unity **6000.6.6f1** (`unityhub://6000.6.6f1/d20c9ac777da`). The player carries its own MuJoCo runtime, so nothing else needs installing.

```bash
git clone --filter=blob:none --sparse https://github.com/Sharun692/VR_space.git
cd VR_space
git sparse-checkout set spacerobot-unity-mujoco-vr/linux
cd spacerobot-unity-mujoco-vr/linux/packages
unzip spacerobot-unity-mujoco-linux-player.zip
unzip spacerobot-unity-mujoco-project.zip
./SpaceRobot_Unity_MuJoCo_Build/Run_Simulation.sh
```

The first launch of a freshly extracted build is slow, because Unity compiles its shaders before the window appears. Later runs start in a few seconds.

The camera orbits on a left drag, pans on a right or middle drag, zooms on the wheel and recentres on F. `-capture <path> -captureAt <seconds>` writes one frame at a given simulated time and exits.

The Unity project is `SpaceRobotMj`. The scene and the checks are described in `docs/unity-scene.md`.

## How the scene is built

The scene is generated by script. The editor command **SpaceRobot → Build in-Unity MuJoCo scene** imports `tools/spacerobot_high_fidelity.xml`, applies the required settings, attaches the mission components and saves `Assets/SpaceRobot/Scenes/SpaceRobot_Service_Mj.unity`.

`SpaceRobotMission` steps the simulation from `MjScene.preUpdateEvent` and publishes force samples. `MissionController` holds the gait, the cap sequence and the latch logic. `Stabilization` covers station keeping, attitude hold, the display orbit and limb Cartesian control. `ContactClassifier` measures contacts each step. `MjModelAccess` gives named access to `mjModel` and `mjData`.

## Changes to the MuJoCo Unity plug-in

The included copy of `org.mujoco` 3.11.0 is modified. The model will not import correctly without these changes.

`MjBody` and `MjMocapBody` read only the `quat` attribute of a body transform, ignoring `euler`, `axisangle`, `xyaxes` and `zaxis` without warning. Both rear limbs of this model are `euler="0 0 3.14159265"` and imported unrotated. Both now call `MjEngineTool.ParseTransformMjcf`.

`MjConnect` handled only the `body1`/`body2` form of the connect constraint. The four rail latches and the cap grasp use the site form, so the import failed with a null reference. It now parses sites, reads `active`, and can engage or release a constraint during simulation.

`MjMeshFilter` called `Object.GetInstanceID()`, which Unity 6 rejects. The call was replaced.

`MjScene` collected hierarchy roots with `FindObjectsByType`, whose order is unspecified. Those roots set body order in the regenerated MJCF, which sets contact ordering in the solver, so trajectories differed between runs. Roots are now ordered by hierarchy path.

On first open the plug-in's `MujocoBinaryRetriever` copied MuJoCo from a system install into the package, raising an error where no install was present and creating a duplicate that broke the build where one was. It is removed, since the libraries ship in `Assets/Plugins/x86_64`.

The scene builder also settles three things the plug-in would otherwise get wrong. The plug-in replaces the model's timestep with `Time.fixedDeltaTime`, integrating at 20 ms instead of 1 ms. Without `MjGlobalSettings.UseRawGameObjectNames`, every MuJoCo element gains a numeric suffix and lookups by name fail. Material colours are not preserved through the components, so the builder reads them from the original MJCF.

## Validation

Both versions were started from an identical reset state with zero control and run for five seconds of free dynamics, then compared joint by joint with quaternion sign accounted for. The largest error across 59 joints was 6.6 × 10⁻¹⁰, the mean 5.3 × 10⁻¹¹. The compiled models match in every dimension (`ngeom` 180, `nq` 71, `nv` 69, `nu` 56, `neq` 5), in all element names, and exactly in mass and inertia.

The 150 s mission reaches `cap-task-complete` with no regrasp waits, at least three rail latches held throughout and four cap finger contacts, matching the reference on each. The final cap angle is 0.945914 rad against 0.948172 rad for the reference. Repeated runs reproduce that figure to the last digit, including from a fresh extraction of the archive.

The 2.3 × 10⁻³ rad gap comes from the model, not the rewritten controller. The Python controller run against the model Unity regenerates gives 0.945684 rad, so the two controllers agree to 2.3 × 10⁻⁴ rad on the same input. Unity stores transforms in single precision, so regenerating the model from components shifts body frames by about 10⁻⁷, which 150 s of contact-rich dynamics amplifies.

A bare `mj_step` costs 35 µs. With the control law the mission runs at 260 to 320 µs per step, 3.1 to 3.8 times realtime without rendering, against roughly 620 µs per step for the Python reference.

The plug-in syncs every component transform after each step, which dominates the frame at 1 kHz. The physics is therefore substepped: eleven 1 ms steps per rendered frame with one sync, about 3 ms of an 11.1 ms frame at 90 Hz.

**SpaceRobot → Run in-Unity mission validation** reproduces these figures.

## Force interfaces

`SpaceRobotMission.ForceSampleAvailable` fires once per physics substep with the cap contact force, the four per-limb grip forces and the cap finger contact count.

`SpaceRobotHaptics` maps a measured force to a vibration pulse on an XR controller. It defaults to the grip force of a chosen limb, which covers holding the rail as well as the cap, and can be switched to cap contact alone.

A limb can be driven from a Unity transform, such as a tracked controller: a target position is supplied each frame and MuJoCo resolves the contact. `SpaceRobotHandControl` does that over `MissionController.SetExternalLimb`. Limbs are independent, so two hands can drive two limbs while the remaining two hold the robot to the rail.

At the default gains a limb 25 cm from its target closed to 1.6 mm in four seconds, with two driven together reaching 1.6 mm each. `Stiffness`, `Damping` and `ForceLimit` on the component set the response, and apply only to limbs under external control.
